Copy AI ID Arrow 키보드 네비게이션 규칙 정리

현재 구현에서는 ArrowUp이 부모로 바로 올라가지 않고 이전/왼쪽 sibling을 먼저 선택한다. 요청된 최종 방향은 명확하다. 위쪽 화살표는 항상 부모 우선이어야 하며, 이전/왼쪽 sibling 이동은 ArrowLeft가 담당해야 한다. ArrowDown은 자식이 있으면 반드시 자식으로 먼저 내려가고, 자식이 없을 때에만 직접 오른쪽 sibling으로 넘어가야 한다.

최종 결론
상/하는 계층 이동, 좌/우는 sibling 이동으로 분리
직접 원인
ArrowUp이 previous sibling을 parent보다 먼저 찾도록 구현됨

결론

현재 현상은 hover 문제라기보다 arrow resolver 규칙 문제다. hover는 현재 요소를 highlight로 저장할 뿐이고, 실제 이동 방향은 keydown 이후 navigation resolver가 결정한다. 지금 resolver는 ArrowUp을 previous sibling -> parent 순서로 처리한다.

요청된 규칙은 ArrowUp = parent only이다. 즉 현재 요소에 이전 sibling이 있더라도 위쪽 화살표는 sibling으로 가지 말고 부모 요소로 바로 올라가야 한다. 이전 sibling은 ArrowLeft가 처리하면 된다.

ArrowDown은 이미 “자식 우선”이라는 큰 방향은 맞지만, 현재 구현은 자식과 직접 오른쪽 sibling이 없을 때 조상 branch의 다음 sibling까지 올라가서 이동한다. 요청 문장 기준으로는 자식이 없고, 현재 노드 자신에게 직접 오른쪽 sibling이 있을 때만 오른쪽 sibling으로 이동해야 한다.

핵심 요약

  • ArrowUp 변경 필요: 현재는 이전/왼쪽 sibling을 먼저 찾는다. 새 규칙은 부모 요소로 바로 이동한다.
  • ArrowDown 정리 필요: 자식이 있으면 무조건 첫 자식으로 내려간다. 자식이 없을 때만 직접 오른쪽 sibling으로 이동한다.
  • 좌우 역할 분리: 이전/왼쪽 sibling은 ArrowLeft, 다음/오른쪽 sibling은 ArrowRight 또는 ArrowDown의 leaf fallback에서만 처리한다.
  • 현재 코드 원인: preview 쪽 navigation.ts와 layout tree 쪽 treeKeyboardNavigation.ts 둘 다 ArrowUp을 previous sibling 우선으로 구현하고 있다.
  • 문서 불일치 가능성: README와 docs도 현재 구현 기준으로 “ArrowUp = previous sibling, 없으면 parent”라고 되어 있어, 코드 수정 시 문서도 같이 바꿔야 한다.

1. 요청된 최종 mental model

사용자가 기대하는 방향키 모델은 단순하다. 상/하는 부모-자식 계층 이동이고, 좌/우는 같은 부모 아래의 sibling 이동이다. 따라서 ArrowUp에서 이전 sibling을 먼저 찾는 현재 동작은 이 모델과 맞지 않는다.

키 요청된 기본 의미 우선순위 중요한 금지 사항
ArrowUp 부모 요소로 올라가기 부모만 본다 이전/왼쪽 sibling으로 가지 않는다
ArrowDown 자식 요소로 내려가기 첫 자식 → 직접 오른쪽 sibling 자식이 있는데 sibling으로 가지 않는다
ArrowLeft 이전/왼쪽 sibling으로 이동 직접 previous sibling 부모로 올라가는 키가 아니다
ArrowRight 다음/오른쪽 sibling으로 이동 직접 next sibling 자식으로 내려가는 키가 아니다
짧은 원칙
상: parent
하: first child, 없으면 own next sibling
좌: own previous sibling
우: own next sibling

2. 현재 구현된 arrow 규칙

현재 코드는 preview iframe에서 hover된 실제 DOM 요소를 기준으로 이동하는 규칙과, editor layout tree에서 focus된 row를 기준으로 이동하는 규칙을 별도로 갖고 있다. 두 구현 모두 현재 ArrowUp을 previous sibling 우선으로 처리한다.

키 현재 preview 이동 규칙 현재 layout tree row 이동 규칙
ArrowUp 이전 sibling → 없으면 부모 previousSiblingNodeId → 없으면 parentNodeId
ArrowDown 첫 자식 → 다음 sibling → 조상 next sibling firstChildNodeId → nextSiblingNodeId → ancestor next sibling
ArrowLeft 이전 sibling → 조상 previous sibling branch의 가장 깊은 마지막 descendant previousSiblingNodeId → ancestor previous sibling branch의 last descendant
ArrowRight 다음 sibling → 조상 next sibling branch의 첫 자식 nextSiblingNodeId → ancestor next sibling branch의 first child

3. 직접 원인이 되는 코드 위치

  • Preview DOM navigation: src/content/editor-bridge/navigation.ts
  • Editor layout tree navigation: src/editor/components/tree/treeKeyboardNavigation.ts
  • Hover highlight: src/content/editor-bridge/highlight.ts는 현재 요소를 잡을 뿐, 부모/형제 선택 정책의 원인은 아니다.
현재 preview 쪽 핵심 로직
'arrow-up': 'previous-sibling-or-parent'

case 'previous-sibling-or-parent':
  return findSiblingLayoutElement(element, 'previous')
    ?? resolveParentLayoutElement(element);
현재 layout tree 쪽 핵심 로직
case 'ArrowUp':
  return row.previousSiblingNodeId ?? row.parentNodeId;

case 'ArrowDown':
  return row.firstChildNodeId
    ?? row.nextSiblingNodeId
    ?? findAncestorSiblingNodeId(row, 'next', rowMap);

5. ArrowUp 상세 예시: 현재 vs 요청 규칙

핵심 변경점이다. 현재 구현은 이전 sibling이 있으면 부모를 보지 않는다. 요청 규칙은 이전 sibling이 있어도 무조건 부모로 올라간다.

현재 위치 현재 ArrowUp 결과 요청된 ArrowUp 결과 설명
pricing-link home-link nav pricing-link의 이전 sibling은 home-link지만, 위쪽 화살표는 부모 nav로 가야 한다.
home-link nav nav 이 경우는 이전 sibling이 없기 때문에 현재 구현도 우연히 부모로 간다.
card-b card-a cards card-a 이동은 ArrowLeft의 역할이다. ArrowUp은 cards로 올라가야 한다.
main header body main의 이전 sibling은 header지만, 계층상 부모는 body다.
footer main body footer의 이전 sibling은 main이다. 그러나 위쪽 화살표는 부모 body로 올라가야 한다.

6. ArrowDown 상세 예시: 자식 우선, 그 다음 직접 오른쪽 sibling

ArrowDown은 “내려가기” 동작이다. 따라서 현재 요소에 자식이 있으면 sibling으로 넘어가면 안 된다. 자식이 없을 때에만 같은 부모 아래의 직접 next sibling으로 갈 수 있다.

현재 위치 자식 존재 여부 현재 ArrowDown 결과 요청된 ArrowDown 결과 설명
nav 있음: home-link, pricing-link home-link home-link 자식이 있으므로 첫 자식으로 내려간다. 현재 구현과 요청이 일치한다.
hero 있음: h1, p h1 h1 자식이 있으면 sibling인 cards로 가면 안 된다. 첫 자식 h1이 맞다.
home-link 없음 pricing-link pricing-link 자식이 없고 직접 오른쪽 sibling이 있으므로 다음 sibling으로 갈 수 있다.
pricing-link 없음 main 이동 없음 현재 구현은 조상 header의 next sibling인 main까지 찾아간다. 요청 기준으로는 pricing-link 자신에게 직접 오른쪽 sibling이 없으므로 이동하지 않는다.
card-b 없음 footer 이동 없음 현재 구현은 조상 main의 next sibling인 footer로 넘어갈 수 있다. 요청 기준으로는 card-b의 직접 next sibling이 없으므로 멈춘다.

7. ArrowLeft / ArrowRight 역할 정리

사용자가 말한 핵심은 “left sibling은 왼쪽 키를 누르면 된다”는 것이다. 즉 이전 sibling 이동을 ArrowUp에 섞으면 안 된다. sibling 이동은 좌우 키의 책임으로 분리하는 편이 예측 가능하다.

키 권장 기본 동작 예시 비고
ArrowLeft 직접 previous sibling pricing-link → home-link 이 동작 때문에 ArrowUp이 previous sibling을 처리할 필요가 없다.
ArrowRight 직접 next sibling home-link → pricing-link 오른쪽 sibling 이동은 ArrowRight의 기본 역할이다.
주의: 현재 구현은 ArrowLeft/ArrowRight도 조상 branch를 타고 이동하는 확장 fallback을 갖고 있다. 이 fallback을 유지할지 제거할지는 별도 제품 결정이지만, 최소한 ArrowUp에서는 previous sibling fallback을 제거해야 요청과 일치한다.

8. 수정 후 기대 규칙 명세

아래 규칙은 사용자의 설명을 기준으로 정리한 “명확하고 예측 가능한” 최종 명세다. 구현 시 preview DOM navigation과 editor layout tree navigation에 동일하게 적용되어야 한다.

상황 ArrowUp ArrowDown ArrowLeft ArrowRight
부모 있음, 자식 있음, 양쪽 sibling 있음 부모 첫 자식 이전 sibling 다음 sibling
부모 있음, 자식 없음, 오른쪽 sibling 있음 부모 다음 sibling 이전 sibling이 있으면 이동 다음 sibling
부모 있음, 자식 없음, 오른쪽 sibling 없음 부모 이동 없음 이전 sibling이 있으면 이동 이동 없음
루트 또는 부모 없음 이동 없음 첫 자식이 있으면 이동 이동 없음 직접 next sibling이 있으면 이동

9. 구현 변경 포인트

실제 수정은 크지 않다. 핵심은 ArrowUp에서 previous sibling을 제거하고, ArrowDown에서 조상 next sibling fallback을 제거할지 결정하는 것이다. 사용자의 현재 설명 기준으로는 제거하는 쪽이 맞다.

Preview navigation 제안
// ArrowUp
case 'parent':
  return resolveParentLayoutElement(element);

// ArrowDown
case 'first-child-or-own-next-sibling':
  return findFirstChildLayoutElement(element)
    ?? findSiblingLayoutElement(element, 'next');
Layout tree navigation 제안
case 'ArrowUp':
  return row.parentNodeId;

case 'ArrowDown':
  return row.firstChildNodeId ?? row.nextSiblingNodeId;

10. 최종 예시 모음

예시 A: pricing-link에서 ArrowUp

현재 위치는 body > header > nav > pricing-link이다.

  • 현재 구현: previous sibling인 home-link로 이동한다.
  • 요청 규칙: parent인 nav로 이동한다.
  • 이유: previous sibling 이동은 ArrowLeft의 역할이다.

예시 B: card-b에서 ArrowUp

현재 위치는 body > main > cards > card-b이다.

  • 현재 구현: previous sibling인 card-a로 이동한다.
  • 요청 규칙: parent인 cards로 이동한다.
  • 이유: 위쪽 화살표는 같은 레벨 탐색이 아니라 상위 계층으로 올라가는 키다.

예시 C: hero에서 ArrowDown

현재 위치는 body > main > hero이고, hero에는 h1과 p 자식이 있다.

  • 현재 구현: 첫 자식 h1로 이동한다.
  • 요청 규칙: 첫 자식 h1로 이동한다.
  • 이유: 자식이 있으면 오른쪽 sibling인 cards로 넘어가면 안 된다.

예시 D: home-link에서 ArrowDown

현재 위치는 body > header > nav > home-link이고, home-link에는 자식이 없다.

  • 현재 구현: 직접 next sibling인 pricing-link로 이동한다.
  • 요청 규칙: 직접 next sibling인 pricing-link로 이동한다.
  • 이유: 자식이 없고, 현재 노드 자신에게 오른쪽 sibling이 있으므로 fallback 이동이 허용된다.

예시 E: pricing-link에서 ArrowDown

현재 위치는 body > header > nav > pricing-link이고, pricing-link에는 자식도 직접 next sibling도 없다.

  • 현재 구현: 조상 branch를 타고 main으로 이동할 수 있다.
  • 요청 규칙: 이동하지 않는다.
  • 이유: “나에게 오른쪽 sibling이 있을 때만” 다음 sibling fallback이 허용되기 때문이다.
