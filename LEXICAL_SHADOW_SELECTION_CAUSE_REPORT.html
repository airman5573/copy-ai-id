Copy AI ID Notebook 입력 누락 원인 분석

노트 에디터에서 hello world를 입력했는데 실제 DOM에는 eowrd처럼 일부 글자가 누락된 문제에 대한 원인, 증거, 수정 내용을 정리한 문서입니다.

최종 결론
ShadowRoot selection과 Lexical의 window selection 기준 불일치
수정 커밋
8143762 Fix notebook shadow selection typing

결론

직접 원인은 Lexical 노트 에디터가 ShadowRoot 안에서 동작하는데, Lexical 내부 입력 처리 로직은 실제 ShadowRoot selection이 아니라 window.getSelection() / document selection을 기준으로 caret 위치를 판단한 것입니다.

사용자가 보기에는 “글자 하나 입력할 때마다 focus가 사라지는 것”처럼 보였지만, WebmateLog상 핵심 패턴은 반복적인 의도적 blur가 아니라 document selection은 바깥 문서의 HTML/body 쪽을 가리키고, 실제 caret은 shadowRoot.getSelection() 안에 남아 있는 상태였습니다.

이 불일치 때문에 Lexical이 현재 입력 위치를 잘못 해석하거나 이전 내부 selection을 기준으로 controlled insertion/composition 경로를 처리했고, 그 결과 실제 Lexical DOM과 editor state에서 글자가 누락되었습니다. 따라서 단순 복사/export 문제도, Tailwind 경고도, fallback data-ai-id 문구도 핵심 원인이 아니었습니다.

핵심 요약

  • 문제 위치: Chrome extension overlay의 notebook Lexical contenteditable이 ShadowRoot 내부에 mount됨.
  • 직접 원인: 실제 caret은 ShadowRoot selection에 있었지만 Lexical은 window/document selection을 읽음.
  • 증상: 입력 텍스트가 export나 copy 단계가 아니라 실제 contenteditable DOM 단계에서 이미 누락됨.
  • 오해하기 쉬운 지점: blur처럼 보였지만, 주요 타이핑 구간에서는 highlight blur 로직이 willBlur: false였고 반복 blur가 직접 원인은 아니었음.
  • 보조 원인: chip은 token 성격의 Lexical TextNode라 chip 뒤 caret 위치가 불명확하면 첫 입력이 더 취약해짐.
  • 수정: 노트 에디터 활성 상태에서만 window.getSelection()을 ShadowRoot selection으로 보정하고, chip 삽입 직후 caret을 trailing space 끝으로 명시 이동.

0. 용어와 구조 설명

아래 설명은 이번 문제를 이해하기 위한 기본 개념입니다. 핵심은 “브라우저에는 문서 전체의 selection과 ShadowRoot 내부의 selection이 구분될 수 있고, Lexical은 기본적으로 문서 전체 쪽 selection을 읽는다”는 점입니다.

0.1 Chrome extension ShadowRoot란 무엇인가

ShadowRoot는 브라우저의 Web Components 기능 중 하나인 Shadow DOM의 루트 노드입니다. 쉽게 말하면, 페이지 안에 작은 독립 DOM 공간을 하나 더 만드는 기능입니다.

Chrome extension이 웹페이지 위에 overlay UI를 띄울 때 ShadowRoot를 자주 사용합니다. 이유는 확장 프로그램 UI가 현재 페이지의 CSS, JavaScript, DOM 구조와 섞이지 않게 하기 위해서입니다.

간단한 구조
일반 웹페이지 document
└─ html
   └─ body
      ├─ 페이지 원래 콘텐츠
      └─ copy-ai-id-editor-host
         └─ #shadow-root
            ├─ style
            └─ Copy AI ID editor UI
               └─ Lexical contenteditable

여기서 copy-ai-id-editor-host는 바깥 document에 붙어 있지만, 실제 editor UI는 그 아래의 #shadow-root 내부에 있습니다. 이 내부 공간은 바깥 document와 DOM 경계가 생깁니다.

0.2 왜 바깥과 안을 구분하는 구조를 만들었나

확장 프로그램은 어떤 웹사이트에서도 동작해야 합니다. 웹사이트마다 전역 CSS가 다르고, 버튼/입력창/텍스트에 적용되는 스타일도 제각각입니다. 확장 프로그램 UI를 그냥 페이지 body에 넣으면 페이지 CSS가 extension UI를 깨뜨릴 수 있고, 반대로 extension CSS가 페이지를 망가뜨릴 수 있습니다.

ShadowRoot를 쓰는 이유 효과
CSS 격리 페이지의 button, div, input 전역 스타일이 extension UI에 덜 영향을 줌.
DOM 충돌 방지 페이지의 query selector, 이벤트 위임, 스타일 reset과 extension UI가 덜 섞임.
UI 안정성 어떤 사이트 위에서도 extension panel이 비슷한 모양으로 보일 가능성이 높아짐.

따라서 현재 구조 자체는 이상한 구조가 아닙니다. Chrome extension overlay UI에서는 흔히 선택하는 구조입니다. 문제는 일반 버튼/패널 UI에는 ShadowRoot가 좋지만, contenteditable 기반 rich text editor는 selection 처리에서 ShadowRoot 경계에 민감하다는 점입니다.

0.3 window.getSelection()은 무엇인가

window.getSelection()은 브라우저가 제공하는 표준 API입니다. 현재 사용자가 문서에서 선택한 텍스트 영역이나 caret 위치를 Selection 객체로 돌려줍니다.

텍스트를 드래그해서 선택하거나, contenteditable 안에 커서를 두면 브라우저는 “현재 selection”을 갖습니다. 이 selection에는 anchor/focus node와 offset이 들어 있습니다.

Selection 객체가 담는 대표 정보
const selection = window.getSelection();

selection.anchorNode   // selection 시작 지점의 DOM node
selection.anchorOffset // anchorNode 안에서의 offset
selection.focusNode    // selection 끝 지점의 DOM node
selection.focusOffset  // focusNode 안에서의 offset
selection.isCollapsed  // 드래그 선택이 아니라 caret 하나만 있으면 true

일반 contenteditable editor는 이 API를 통해 “지금 사용자가 어느 글자 뒤에 입력하려 하는지”를 파악합니다. Lexical도 내부적으로 이 계열의 selection 값을 읽어 DOM selection과 자체 editor selection을 동기화합니다.

0.4 바깥 document selection이란 무엇인가

이 보고서에서 말하는 바깥 document selection은 ShadowRoot 내부가 아니라, 웹페이지의 일반 document 기준으로 얻은 selection을 의미합니다. 구체적으로는 window.getSelection() 또는 document.getSelection()으로 읽는 selection입니다.

반대로 안쪽 selection은 ShadowRoot가 별도로 제공하는 shadowRoot.getSelection() 기준 selection입니다. 이 값은 ShadowRoot 내부 contenteditable의 실제 caret 위치를 더 정확히 표현할 수 있습니다.

구분 읽는 API 이번 문제에서의 의미
바깥 document selection window.getSelection() 일부 순간 HTML 또는 body 같은 editor 바깥 node를 가리킴.
안쪽 ShadowRoot selection shadowRoot.getSelection() 실제 사용자의 caret이 있는 노트 editor 내부 text node를 가리킴.
이번 버그에서 문제가 된 상태
사용자는 노트 에디터에 커서를 둠

window.getSelection()
→ 바깥 document의 HTML/body 쪽을 가리킬 수 있음

shadowRoot.getSelection()
→ 실제 노트 에디터 내부 text node와 offset을 가리킴

Lexical은 window.getSelection() 쪽을 기준으로 처리
→ 실제 caret 위치와 다른 기준으로 입력 처리

0.5 바깥과 안의 차이가 실제로 왜 문제가 되는가

contenteditable editor는 “현재 caret이 어느 text node의 몇 번째 글자 뒤에 있는가”를 매우 정확히 알아야 합니다. 그래야 다음 입력 문자를 정확한 위치에 넣을 수 있습니다.

그런데 바깥 document selection은 editor 내부 caret을 놓치고, 안쪽 ShadowRoot selection만 실제 caret을 알고 있는 상태가 되면 editor 라이브러리는 잘못된 지도를 보고 길을 찾는 셈이 됩니다.

editor가 알아야 하는 것 selection mismatch 때 생기는 문제
입력할 text node 바깥 document node를 보고 editor 내부 text node를 찾지 못할 수 있음.
삽입 offset 실제 caret 위치와 다른 offset에 삽입하려고 하거나 기존 selection을 재사용함.
composition 상태 IME/composition 처리 중 들어온 문자가 commit되지 않거나 rollback될 수 있음.
DOM reconciliation 브라우저가 잠깐 넣은 DOM 문자를 Lexical이 자기 state와 맞지 않는다고 보고 제거할 수 있음.

그래서 이번 증상은 “화면에서는 입력한 것 같은데 최종 DOM에는 일부 글자만 남는 현상”으로 나타났습니다. 사용자는 연속 입력했지만, Lexical은 모든 입력을 같은 caret 기준으로 안정적으로 받아들이지 못했습니다.

0.6 Lexical state란 무엇인가

Lexical state는 Lexical editor가 내부적으로 관리하는 문서 모델입니다. 브라우저 DOM 그 자체가 원본 데이터가 아니라, Lexical은 별도의 editor state를 갖고 있고 그 state를 기준으로 DOM을 렌더링합니다.

쉽게 말하면 DOM은 화면에 보이는 결과물이고, Lexical state는 그 결과물을 만들기 위한 원본 문서 데이터입니다. React state와 비슷하게 생각할 수 있습니다.

Lexical의 기본 흐름
사용자 입력 이벤트
→ Lexical이 selection과 입력 내용을 해석
→ Lexical editor state 업데이트
→ 업데이트된 state를 기준으로 DOM reconciliation
→ contenteditable DOM이 다시 맞춰짐

이번 report에서 “Lexical state에 글자가 commit되지 않았다”는 말은, 사용자가 키를 눌렀더라도 그 문자가 Lexical의 내부 문서 모델에 정상 반영되지 않았다는 뜻입니다. 내부 state에 반영되지 않은 문자는 이후 DOM reconciliation에서 사라질 수 있습니다.

용어 이번 문맥에서의 뜻
DOM 브라우저 화면에 실제로 존재하는 element/text node 구조.
Lexical state Lexical이 원본으로 삼는 editor 문서 모델. paragraph, text node, chip node, selection 등이 포함됨.
commit 입력 문자가 임시 DOM 변화가 아니라 Lexical state의 정식 변경으로 반영되는 것.
reconciliation Lexical state와 실제 DOM을 다시 맞추는 과정. state에 없는 DOM 변화는 제거될 수 있음.

0.7 이번 문제를 한 장면으로 요약

문제 장면
사용자가 보는 화면:
  chip 뒤에 caret이 있고 hello world를 입력함

브라우저 ShadowRoot 기준:
  shadowRoot.getSelection()은 editor 내부 text node를 가리킴

바깥 document 기준:
  window.getSelection()은 순간적으로 HTML/body 쪽을 가리킴

Lexical 기준:
  window.getSelection()을 읽고 입력 위치를 계산함

결과:
  일부 입력이 Lexical state에 반영되지 않음
  실제 DOM에도 일부 문자만 남음
  hello world → eowrd 같은 누락 발생

그래서 수정은 “ShadowRoot를 없앤다”가 아니라, 현재 구조를 유지하면서 노트 에디터가 active인 순간에만 Lexical이 실제 ShadowRoot caret을 보도록 selection 값을 연결해주는 방식으로 적용했습니다.

1. 실제로 발생한 현상

사용자가 의도한 입력은 chip 뒤에 hello world가 붙는 것이었습니다. 그러나 실제 DOM은 다음처럼 chip 뒤 텍스트가 eowrd가 되었습니다.

관측된 DOM
<div aria-label="이 요소에 남길 코멘트를 작성하세요..."
     class="copy-ai-id-editor-note-contenteditable"
     contenteditable="true"
     data-ai-id="copy-ai-id-editor-note-lexical-editor"
     data-lexical-editor="true">
  <p dir="auto">
    <span class="copy-ai-id-editor-note-chip"
          data-copy-ai-id-chip-id="el-1">el-1</span>
    <span data-lexical-text="true"> eowrd</span>
  </p>
</div>

이 DOM이 중요한 이유: 최종 copy 문자열이나 draft export에서만 글자가 잘린 것이 아니라, Lexical이 렌더링한 실제 editor DOM 자체가 이미 잘못된 상태였습니다. 즉, 원인은 copy 함수나 chip target map 붙이는 함수보다 앞단인 입력 처리 단계에 있었습니다.

2. 컴포넌트 구조상 위험 지점

노트 에디터 UI는 extension overlay host에 ShadowRoot를 만들고 그 안에 React/Lexical 앱을 mount하는 구조였습니다. 이 구조는 CSS 격리에는 좋지만, contenteditable selection을 다루는 에디터 라이브러리에는 민감합니다.

항목 내용
UI mount 위치 src/editor/main.tsx에서 host.attachShadow({ mode: 'open' }) 사용
입력 컴포넌트 @lexical/react의 ContentEditable
문제 조건 contenteditable이 ShadowRoot 내부에 있고, Lexical은 window/document selection을 읽음
사용자 증상 caret은 보이는 것 같지만 글자 일부가 Lexical state에 반영되지 않음
관련 코드: ShadowRoot mount
// src/editor/main.tsx
const hadExistingShadowRoot = Boolean(host.shadowRoot);
const shadow = host.shadowRoot ?? host.attachShadow({ mode: 'open' });
shadow.replaceChildren();

3. WebmateLog에서 드러난 핵심 패턴

console stack trace만으로는 “어느 selection을 Lexical이 보고 있는지”가 보이지 않았습니다. WebmateLog에 document selection과 shadow selection을 함께 찍으면서 다음 패턴이 확인되었습니다.

관측 항목 의미
highlight-blur-decision에서 willBlur: false highlight 변경이 의도적으로 editor를 blur시키는 문제는 이미 제거되어 있었음.
typing 중 documentSelection.anchor가 HTML 쪽으로 이동 window/document 기준 selection은 editor 내부 caret을 안정적으로 표현하지 못했음.
동시에 shadowSelection은 editor text node 내부를 가리킴 사용자의 실제 caret은 ShadowRoot 내부에 있었음.
composition/input 구간에서 draft length가 증가 후 되돌아감 일부 입력이 Lexical 내부 state에 commit되지 않거나 rollback된 정황.
chip 삽입 직후 focus snapshot이 preview iframe 쪽을 보여준 구간 존재 chip 삽입과 focus 복구 사이에 caret boundary가 취약해질 수 있었음.

정리: “진짜로 매 글자마다 editor가 blur된다”가 아니라, “Lexical이 읽는 selection과 브라우저가 실제로 유지하는 ShadowRoot selection이 서로 다르다”가 핵심이었습니다.

4. Lexical 내부 동작과 충돌한 지점

Lexical 0.45.0의 관련 소스에서 DOM selection을 얻는 경로는 ShadowRoot selection이 아니라 window selection입니다. contenteditable이 일반 document에 있으면 이 방식이 자연스럽지만, ShadowRoot 내부에 있으면 document selection과 shadow selection이 갈라질 수 있습니다.

Lexical selection 경로
// node_modules/lexical/src/LexicalUtils.ts
export function getDOMSelection(targetWindow: null | Window): null | Selection {
  return !CAN_USE_DOM ? null : (targetWindow || window).getSelection();
}

export function getDOMSelectionFromTarget(
  eventTarget: null | EventTarget,
): null | Selection {
  const defaultView = getDefaultView(eventTarget);
  return defaultView ? defaultView.getSelection() : null;
}
selectionchange 처리
// node_modules/lexical/src/LexicalEvents.ts
function onDocumentSelectionChange(event: Event): void {
  const domSelection = getDOMSelectionFromTarget(event.target);
  if (domSelection === null) {
    return;
  }
  const nextActiveEditor = getNearestEditorFromDOMNode(domSelection.anchorNode);
  ...
}

위 코드 때문에 window.getSelection()이 바깥 문서의 HTML 노드를 반환하면, Lexical은 “현재 selection이 editor 안에 있는지”, “어느 text node offset에 삽입해야 하는지”를 잘못 판단할 수 있습니다. 이때 beforeinput/input/composition 처리가 실제 caret과 다른 기준으로 진행되면서 글자 누락이 발생했습니다.

5. 왜 hello world가 eowrd가 될 수 있었나

최종 문자열이 단순히 끝에서 잘린 것이 아니라 중간중간 빠졌다는 점이 중요합니다. 이는 “문자열 후처리 trim”보다 “입력 이벤트 처리 중 일부 character insertion이 누락 또는 rollback”되었을 가능성이 높다는 신호입니다.

  1. 사용자가 chip 뒤에 입력을 시작합니다.
  2. 실제 caret은 ShadowRoot 내부 text node에 있습니다.
  3. 하지만 일부 순간 Lexical이 읽는 window.getSelection()은 바깥 document 쪽을 가리킵니다.
  4. Lexical은 이 selection을 기준으로 editor 내부 selection을 동기화하거나, 기존 internal RangeSelection을 재사용합니다.
  5. composition/beforeinput/input 이벤트가 빠르게 이어지면서 일부 문자는 DOM에 들어갔다가 Lexical reconciliation에서 제거되거나, 아예 올바른 위치에 commit되지 않습니다.
  6. 그 결과 사용자는 연속으로 타이핑했지만, editor state에는 일부 문자만 남습니다.

핵심: 이 문제는 “복사할 때 문자열이 사라진다”가 아니라 “입력 중 editor state 자체가 잘못 만들어진다”입니다. 그래서 실제 DOM에서 이미 eowrd가 보인 것입니다.

6. chip boundary가 증상을 더 잘 드러낸 이유

chip은 일반 텍스트가 아니라 Lexical custom TextNode입니다. token 성격을 가지며 chip 앞뒤에 텍스트를 직접 삽입하지 못하도록 설정되어 있습니다. 따라서 chip 바로 뒤 caret 위치가 불안정하면 첫 글자 입력에서 문제가 더 쉽게 드러납니다.

chip node 특성
// src/editor/notebook/lexical/ChipNode.ts

  return true;

canInsertTextBefore(): boolean {
  return false;
}

canInsertTextAfter(): boolean {
  return false;

기존 삽입 로직은 chip과 trailing space를 함께 넣었지만, RangeSelection 경로에서 caret을 trailing space 끝으로 명시 이동하지 않았습니다. 대부분의 경우 Lexical이 알아서 처리할 수 있지만, ShadowRoot selection mismatch가 있는 상태에서는 이 “약간 애매한 caret 위치”가 첫 입력 누락을 더 쉽게 만들 수 있었습니다.

8. 적용한 수정

수정은 두 단계로 적용했습니다. 첫 번째는 핵심 원인인 ShadowRoot selection mismatch 보정이고, 두 번째는 chip 삽입 직후 caret boundary를 명시적으로 안정화하는 것입니다.

핵심 수정: Shadow selection bridge
// src/editor/shadow-selection-bridge.ts
const previousGetSelection = window.getSelection;
const getDocumentSelection = (): Selection | null => previousGetSelection.call(window);

const patchedGetSelection = function patchedCopyAiIdGetSelection(): Selection | null {
  const documentSelection = getDocumentSelection();
  const noteEditor = getNoteEditorElement(shadowRoot);
  const shadowSelection = getShadowSelection(shadowRoot);

  if (noteEditor && shadowSelection && shouldUseShadowSelection({
    documentSelection,
    host,
    noteEditor,
    shadowRoot,
    shadowSelection,
  })) {
    return shadowSelection;
  }

  return documentSelection;
};
적용 범위 제한
function shouldUseShadowSelection(...) {
  if (!selectionTouchesNode(shadowSelection, noteEditor)) {
    return false;
  }

  const shadowActiveElement = shadowRoot.activeElement;
  const noteEditorHasFocus = isNodeWithin(shadowActiveElement, noteEditor);
  const hostHasFocusWithoutInnerActiveElement = document.activeElement === host
    && shadowActiveElement === null;
  const documentSelectionWithinEditor = selectionTouchesNode(documentSelection, noteEditor);

  return noteEditorHasFocus
    || (hostHasFocusWithoutInnerActiveElement && !documentSelectionWithinEditor);
}

9. 수정이 문제를 해결하는 방식

수정 전 수정 후
Lexical이 window/document selection을 읽음. 노트 에디터가 active이고 shadow selection이 editor 내부일 때만 ShadowRoot selection을 반환.
document selection이 HTML/body로 튀면 Lexical caret mapping이 흔들림. Lexical이 실제 caret 위치와 같은 selection을 보게 됨.
chip 삽입 후 caret 위치가 trailing space 끝이라고 명시되지 않음. chip 뒤 trailing space 끝으로 selection을 고정.
로그는 console stack trace 중심이라 원인 필터링이 어려움. 필요 시 shadow-selection-bridge-used WebmateLog로 보정 동작만 필터 가능.

11. 최종 원인 문장

최종적으로, 문제는 Chrome extension ShadowRoot 내부에 있는 Lexical contenteditable에서 실제 caret은 shadowRoot.getSelection()에 있었지만, Lexical의 입력 처리 경로는 window.getSelection()을 읽어서 바깥 document selection을 기준으로 글자 삽입을 처리한 데서 발생했습니다.

그 결과 입력 중 selection 동기화가 깨지고 일부 글자가 Lexical state에 commit되지 않아, 사용자가 입력한 hello world가 실제 editor DOM에서는 eowrd처럼 누락된 형태로 남았습니다.
